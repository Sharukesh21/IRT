# Phase 6 — Production Incident Integration, CI/CD & Automated Regression Orchestration

## 1. Objective

Phase 6 closes the capstone loop by connecting production-like incident ingestion to automated CI/CD regression verification. When a new production incident arrives, the system automatically identifies which regression tests are relevant, executes them in a targeted suite, and returns a machine-readable PASS/FAIL signal compatible with CI pipelines.

---

## 2. Production Incident Ingestion

### Schema

External incidents arrive as structured JSON payloads:

```json
{
  "external_incident_id": "PROD-4821",
  "title": "Duplicate submission detected",
  "severity": "HIGH",
  "failure_type": "DUPLICATE",
  "event_type": "SUBMIT_REQUESTED",
  "category": "DUPLICATION",
  "service": "exam-submission",
  "source": "PRODUCTION_API"
}
```

### Processing Pipeline

1. **RECEIVED** — Raw payload stored immediately.
2. **VALIDATED** — Schema verified, required fields present.
3. **NORMALIZED** — Mapped to internal `Incident` model with `INC-XXXX` identifier.
4. **DEDUPLICATION** — Fingerprint `FAILURE_TYPE:EVENT_TYPE` checked against existing groups. If matched, occurrence count is incremented.
5. **PROCESSED** — Incident stored, group updated, response returned.

### Idempotency

The same `external_incident_id` submitted multiple times returns the existing record with status `DUPLICATE` — it is not re-processed.

---

## 4. Deduplication

Uses the same fingerprinting from Phase 4:

```
fingerprint = f"{failure_type}:{event_type}"
```

If an `IncidentGroup` with the same `group_key` exists, a new occurrence is recorded and `occurrence_count` is incremented rather than creating an unrelated new incident.

---

## 5. Incident Prioritization

Deterministic rules (no AI):

| Condition | Priority |
|-----------|----------|
| CRITICAL + HIGH frequency | P0 |
| HIGH + state corruption | P1 |
| MEDIUM | P2 |
| LOW | P3 |

---

## 6. Regression Test Mapping & Relevance Scoring

The `RegressionOrchestrator` scores every active test against the incident using deterministic rules:

| Rule | Points |
|------|--------|
| Exact incident link (`test.incident_id == incident.id`) | +100 |
| Same fingerprint | +80 |
| Same root cause | +60 |
| Same failure type | +40 |
| Same event type | +30 |
| Same category | +20 |

Tests are sorted descending by score. Only tests with score > 0 are selected in `TARGETED` mode.

**Safety fallback**: If no test scores > 0, the system falls back to `FULL` suite automatically.

---

## 7. Regression Orchestration States

```
CREATED → PLANNING → PREPARING → RUNNING → ANALYZING → PASSED | FAILED | ERROR
```

---

## 8. CI/CD Gateway

### Endpoint

```
POST /api/v1/ci/regression/run
```

Input:
```json
{
  "incident_id": "INC-00081",
  "strategy": "TARGETED",
  "branch": "feature/submission-fix",
  "commit_sha": "abc123"
}
```

Output:
```json
{
  "status": "PASSED",
  "tests": 7,
  "passed": 7,
  "failed": 0,
  "errors": 0
}
```

### Exit Status Semantics

| Status | Meaning |
|--------|---------|
| `PASSED` | All assertions passed |
| `FAILED` | One or more assertions failed (application regression) |
| `ERROR` | Infrastructure failure (DB unavailable, etc.) |

---

## 9. GitHub Integration

- **Webhook**: `POST /api/v1/integrations/github/webhook` — validates HMAC signature when `GITHUB_WEBHOOK_SECRET` is configured.
- **GitHub Actions**: `.github/workflows/regression.yml` — triggers on PR open/synchronize.

---

## 10. Regression Escape Detection

When an incident is re-ingested and the previously linked regression test fails during orchestration:

```
REGRESSION ESCAPE detected
```

A `RegressionEscape` record is created with timestamp, test last status, and explanation. This appears on the CI Dashboard.

---

## 11. Regression Policies

Configurable per-deployment via the UI or API:

- `strategy`: TARGETED | FULL
- `block_on_failure`: true → CI fails; false → warning only
- `required_severity`: minimum severity to trigger

---

## 12. Security

- All webhook payloads are verified via HMAC SHA-256 before processing.
- No shell commands are ever executed from external payloads.
- No arbitrary Python eval or exec on test definitions.
- All inputs validated via Pydantic schemas with length limits.

---

## 13. CLI

```bash
# Run targeted regression for an incident
python cli.py run --incident INC-00081

# Run full suite
python cli.py run --suite

# With commit context
python cli.py run --incident INC-00081 --commit abc123 --branch main
```

## 14. Metrics

| Metric | Formula |
|--------|---------|
| Incident Regression Coverage | Incidents with ≥1 active test / eligible incidents |
| CI Pass Rate | Passing orchestrations / total orchestrations |
| Escape Rate | Escapes / protected incidents |
| Test Reduction (Targeted) | 1 - (targeted tests / full tests) |

---

## 16. Limitations

- GitHub Actions workflow requires a running backend service. In CI, this is started via `uvicorn` within the job.
- Targeted selection is not yet using static code analysis — it relies on explicit failure_type, category, and tag matching.
- The CLI uses `httpx` and requires the backend to be running.
